# Feature Specification: Shared Foundation for Four Independent Workstreams

**Feature Branch**: Not created; feature selection is independent of Git branches.

**Feature Directory**: `specs/000-foundation`

**Owner**: B

**Created**: 2026-11-10

**Status**: Draft for user review

**Input**: User description: "Prepare NoteLens shared agreements, ownership and a key-free foundation so four members can implement separate workstreams against common evidence-preserving records."

**Governing requirements**: [Constitution](../../.specify/memory/constitution.md) and
[source prompt](../../prompts/NoteLens_Codex_SpecKit_prompt_00.md). Implementation choices
belong to the later plan and must preserve the confirmed boundaries.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start Four Independent Workstreams (Priority: P1)

As a team member, I can open my own working copy, identify my owned work and start a ready
task using representative mock inputs without waiting for other members' business modules.

**Why this priority**: Independent work depends on a common, verifiable foundation.

**Independent Test**: Each of A/B/C/D selects the correct feature, reads its handoff and
runs its documented local mock checks without another complete module or real provider keys.

**Acceptance Scenarios**:

1. **Given** the shared foundation checkpoint, **When** all four members open separate
   working copies, **Then** each sees its own specification, plan, tasks, allowed paths,
   first five ready tasks and English start prompt.
2. **Given** another business module is unavailable, **When** a member runs their local
   mock scenario, **Then** agreed mock records permit independent development.
3. **Given** a proposed shared-record change, **When** a member needs it, **Then** the
   request goes to B and affected consumers rather than silently changing shared files.

---

### User Story 2 - Preserve Meaning Across Modules (Priority: P1)

As a demo reviewer, I can follow a document through the sample flow and trace each displayed
claim to an appropriate source, even before real business modules are connected.

**Why this priority**: Shared meaning and evidence prevent inconsistent integration.

**Independent Test**: A public/synthetic fixture goes through preparation, classification,
extraction, summary and chat in mock mode; record validation and quote/highlighting checks
run without external providers.

**Acceptance Scenarios**:

1. **Given** a fixture with a non-BMP character and repeated passages, **When** evidence is
   displayed, **Then** the selected occurrence matches the exact canonical quote and
   code-point interval.
2. **Given** one supported document claim and missing literature evidence, **When** a mixed
   answer is requested, **Then** the supported portion remains available and the gap is shown.
3. **Given** a malformed mock output, **When** validation runs, **Then** it fails explicitly
   instead of being presented as a compliant result.

---

### User Story 3 - Review an Honest Foundation Checkpoint (Priority: P2)

As the team coordinator, I can distinguish prepared documents, tested mock behavior,
unimplemented business tasks and external decisions before colleagues branch from one base.

**Why this priority**: A misleading checkpoint creates integration and schedule risk.

**Independent Test**: Review checkpoint evidence against the artifact inventory and actual
executed commands; unimplemented/live checks remain clearly identified.

**Acceptance Scenarios**:

1. **Given** only specifications exist, **When** status is reported, **Then** module
   implementation and the runnable foundation remain incomplete.
2. **Given** foundation checks pass, **When** the checkpoint is recorded, **Then** actual
   commands/results and approved version-control steps identify the shared base.
3. **Given** a provider budget or hosting account is unknown, **When** local checks run,
   **Then** mock work proceeds without paid calls or invented account information.

### Edge Cases

- A feature is selected incorrectly even though the Git branch name appears correct.
- Members accidentally share a checkout or edit a parent-owned annotation directory.
- A quote exists twice, an emoji changes native string indices, or a canonical digest differs.
- A partial module outage occurs; a document answer must remain independent of literature.
- The directory already contains work, no remote/commit exists, or Git operations are unavailable.
- A documented command does not exist, an optional live check is off, or a source PDF is absent.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Preparation MUST use the official installed workflow and record actual versions,
  invocations, limitations and results; documents merely resembling workflow outputs do not suffice.
- **FR-002**: Establish one shared constitution and five separately owned feature specifications:
  foundation plus A/B/C/D. Each feature MUST later have its own plan and executable task backlog.
- **FR-003**: B MUST coordinate collection of A/C/D proposals and freeze shared versioned records
  before parallel business implementation; preparation MUST not claim that this freeze already occurred.
- **FR-004**: Shared records MUST cover prepared documents, classification, extraction/summary,
  retrieval, answers, provenance and shared error outcomes, with positive and negative examples.
- **FR-005**: Prepared documents MUST preserve one canonical text, identity, source metadata and
  digest. Downstream modules MUST not modify it.
- **FR-006**: Evidence MUST use exact canonical quotes and half-open Unicode code-point intervals.
  Cross-language fixtures MUST cover a non-BMP character and distinct repeated-passage occurrences.
- **FR-007**: Records MUST preserve assertion, temporality and subject independently; optional
  ICD output may only reproduce a source-present code.
- **FR-008**: Classification MUST express supported specialty or uncertain/unsupported outcomes,
  score meaning and model version; raw scores MUST not imply calibration or diagnosis.
- **FR-009**: Retrieval/answers MUST preserve source identifiers, versions, citation links,
  sufficient/insufficient/error outcomes and document/literature/mixed/none distinctions.
- **FR-010**: The runnable foundation MUST include standalone mock inputs/outputs for all modules,
  health stubs and a minimal English end-to-end mock flow, visibly labeled as mock.
- **FR-011**: All foundation checks MUST work without secrets or paid calls. Errors MUST include
  unsupported input, validation, timeout, rate limit, provider outage and insufficient evidence.
- **FR-012**: Provide root/local contributor guidance, an allowed-path matrix, review-routing
  preparation without fictional handles and a later declared-PR-scope check.
- **FR-013**: Provide actual Bash and PowerShell working-copy/feature-selection instructions.
  Do not rely on Git branch names, overwrite another session's feature state or invent a remote.
- **FR-014**: Each handoff MUST include first five ready tasks, shared inputs/outputs, mock
  examples, allowed paths, feature activation and actual local verification commands.
- **FR-015**: Tasks MUST retain standard checkbox/ID syntax and stable global F/A/B/C/D aliases.
  Each executable task needs one owner, a story, deliverable, paths, dependencies, acceptance,
  a real command and distinct mock/module/live completion conditions.
- **FR-016**: Feasibility and cost/privacy decisions MUST be reviewed before freezing dependent
  plans. Unknown budgets/accounts MUST not block local mocks or imply paid-service approval.
- **FR-017**: Preparation MUST implement only the approved foundation in a later implementation
  stage; actual business modules remain for the four members.
- **FR-018**: The foundation checkpoint MUST record what exists, executed checks and remaining
  work. No commit hash, deployment URL, team acceptance or experimental result may be fabricated.
- **FR-019**: Every artifact and demo surface MUST be English. Deadline remains 2026-11-24,
  with first development measurement/threshold decisions targeted for 2026-11-14.
- **FR-020**: Work MUST follow the constitution's approval, ownership, data protection,
  cost control and security rules; optional scope MUST not block core delivery.

### Key Entities *(include if feature involves data)*

- **Prepared document**: Canonical text, identity, digest and permitted source.
- **Module agreement**: Versioned meanings of inputs, outputs, evidence and errors.
- **Feature workstream**: Owner, independent scope, stories, plan, tasks and dependencies.
- **Mock fixture**: Representative valid/invalid input and expected output, explicitly synthetic/public.
- **Checkpoint record**: Actual artifacts/checks, version-control state and unfinished work.
- **Claim provenance**: Links distinguishing patient document evidence from general literature.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Four members can each select the correct feature and perform a documented
  mock check without another completed business module or provider key.
- **SC-002**: Five features have independent specifications, plans and task files before the
  foundation checkpoint; four member handoffs/start prompts identify five ready initial tasks each.
- **SC-003**: All defined acceptance-suite records pass structural checks, and all document
  evidence quotes/offsets match exactly, including non-BMP and repeated-passage cases.
- **SC-004**: The mock demo completes input-to-results and source-preserving question answering;
  every output is English and visibly marked as mock.
- **SC-005**: Every claimed completed check/commit/deployment has recorded evidence; all
  unexecuted live checks and business implementation remain distinguishable.
- **SC-006**: Every owned path has one owner with explicit annotation exceptions, and all four
  working-copy instructions use the same actual foundation base.

## Assumptions

- No new product defaults are inferred. Requirements derive from the supplied prompt and
  explicit session decisions; see [open decisions](../../docs/team/open-decisions.md).
- The two source PDFs are unavailable; the prompt explicitly permits preparation without them.
- The repository exists publicly at the user-approved remote; its publication does not
  authorize pushing this package.
- This specification is a draft. Plans, tasks, contracts, runnable mocks, handoffs, CI and
  checkpoint are future work, not completed by this document.
